Merchant Services · Payment Brand Interchange

PBI PDLC — Neuro — Architecture

The engineering reference: what runs, in what order, reading which files, and what each one is allowed to decide. Read this to work on the system rather than to be briefed on it.

Slice  interchange · Stratus code · PeopleSoft rates Stages  six, five gates External writes  two, both gated

01 — The spine

Six stages, five gates, two writes

Each stage is a separate agent session started by its own prompt file. The agent surfaces the next transition; it never issues it. Context hygiene is the reason — every stage starts clean, so nothing leaks between them except artifacts on disk.

02 — Layout

Where everything lives

Four trees, and the split between them is the whole extensibility story: core/ is generic and never varies; core/profiles/<domain>/ and core/templates/<domain>/ are the domain seam; overlays/ is the runtime-tool seam; runs/ is per-run state and is disposable.

# the generic core — a new domain changes none of this
core/
  scripts/        ~40 deterministic steps: clone, code_map_build, doc_index,
                  merge_manifest, apply_enrichment, jira_plan, jira_validator,
                  jira_push, code_push, tier_walk, ledger, gate, telemetry…
  skills/         12 instruction modules — the model's half of the work
  checks/         build-time guards (§10): disposition totality, index completeness
  extractors/     per-LANGUAGE, frozen, deterministic (c_extractor.py)
  code_profiles/  per-REPO reading rules (c_repo, mixed_repo)
  estate/         applications.yaml · interfaces.yaml   ← proposed, 003.2

# the domain seam — a new domain rewrites exactly this
core/profiles/payment_brand/
  si_profile.payment_brand.yaml        the 18 SI sections + must_capture
  change_types/<type>/                 flow.yaml · probes.yaml · *.skill.md
core/templates/payment_brand/
  jira_template.payment_brand.yaml     SI section → Jira field mapping

# the runtime-tool seam — claude and copilot, kept at parity by a build check
overlays/{claude,copilot}/             agents, prompt files, launch

# proof — every subsystem owns a fixture that must stay green
fixtures/<subsystem>/verify_*.py       31 of them; zero for Stage 5 (TASK-009)

# per-run, disposable
runs/<run_id>/  UI_INPUT.yaml · context_set/ · code_map/ · solution_intent/
                enrichment.json · jira_plan.json · code_changes/ · ledger/
Two seams only

The domain seam (SI section profile + jira_template) and the runtime-tool seam (instruction file, prompt files, launch). Two further variation points are not domain concerns: the per-language extractor, behind an onboarding gate, and the per-repo signal profile. Nothing else varies. If a change needs a new place to vary, the declaration was not expressive enough — that is the finding, not the workaround.

03 — Stage detail

What each stage reads and writes

Stage Reads Writes What it is allowed to decide
0 · Config operator input via the UI UI_INPUT.yaml, run scaffold Repo, domain, uploaded artifacts and their dispositions, and a change-type hypothesis. The hypothesis is never authoritative.
1 · Ingest extractor_manifest, code_profiles/*, retrieval_config context_set/, code_map/ Nothing structural. The extractor is frozen and deterministic; the model contributes only purpose text. Modules and edges are derived.
2 · Intent v1 si_profile, probes.yaml, the history KB v1.md — frozen at G1 What is being asked, code-blind by choice. Classifies every §8 assertion as modify_existing / new_capability / unclear, and answers the probes.
3 · Enrichment flow.yaml, applications.yaml, interfaces.yaml, networks.yaml, v1 assertions, the code map, the source enrichment.json, v2.md Where the change lands, and where it does not. Files findings, non-events, boundaries. Never edits v1.
4 · Jira plan v2 §16 + §7, jira_template jira_plan.json → Jira Epic and story shape, acceptance criteria. Acceptance criteria are authored here and exist nowhere upstream — that is what makes this a translation, not a copy.
5 · Code change plan + §16 + repo code_changes/ → branch The diff itself, as reviewable copies. EDIT stories only; VERIFY and VALIDATE become notes. Every hunk cites its §16 entry.
Why v1 is code-blind on purpose

The code map already exists by Stage 2 — ingest built it. v1 does not use it by choice. That is what makes the audit story work: every difference between v1 and v2 traces to a numbered, code-checked finding. If v1 peeked at the code, that guarantee dissolves and nobody could say which claims were requirements and which were observations.

04 — Files in the flow

Which declaration is read, and when

Eleven declarations decide what a run does. None of them branch in code — each is joined to the next by a named key, so the whole analysis is the transitive closure of those joins. Note how little Stage 5 reads: by then every decision has been made and written down.

File Family Read by What it decides
core/estate/applications.yaml estateStage 3 What applications exist and what each is made of — a list of substances per application. Also in_estate (do we analyse it?) versus acquired (can we read its code yet?), which are different questions.
core/estate/interfaces.yaml estateStage 3 The file interfaces — MPT, PTI Gen, submission. Each names its parties by role with a writes_at, reads_at and layout_at per side. It is what makes impact cross from one application to another; generic, never re-declared per change type.
change_types/<type>/flow.yaml change typeStage 3 The analysis for one change type: floor, resolve, impact, release_shape. Order is derived from provides/needs, never written.
change_types/<type>/probes.yaml change typeStage 2 The questions asked at Stage 2 that change what runs at Stage 3. Each probe carries activates: [pass id] — one direction only, so a pass never names its probes.
si_profile.payment_brand.yaml documentStage 2 The 18 SI sections, each with its must_capture, its authored stage, what enrichment may touch, and the classes routing row that decides which uploads feed it. must_capture doubles as the semantic retrieval query.
jira_template.payment_brand.yaml documentStage 4 Maps v2 sections onto the Jira hierarchy, one source per level. Type sections map when present and are skipped when absent — adding a change type cannot break the plan for runs without it.
interchange_networks.yaml documentStage 3 The network vocabulary — the designator families each card network publishes. Reference data for resolution, not a rule about what runs.
code_profiles/*.profile.yaml plumbingStage 1 Per-repo reading rules: module clustering, edge derivation. Frozen, deterministic, never model-rewritten at runtime. Referenced from an application's code substance, so each application declares how its own repo is read.
core/extractor_manifest.yaml plumbingStage 1 The per-language extractor freeze: which extractor, under what tooling, with its coverage floor and the git blob sha of the frozen file. A human freezes it by committing; a post-freeze edit cannot pass silently.
core/retrieval_config.yaml plumbingStages 1–2 The calibrated numbers behind the two-level retrieval funnel — whole-read versus index-guided, checked across the routed set rather than per document. Properties of the model and corpus, deliberately not per-run config.
runs/<run>/UI_INPUT.yaml plumbingStage 0→1 Per-run operator configuration reviewed at G0 — repo, domain, uploaded artifacts and their dispositions, and the change-type hypothesis Stage 2 may overturn.

05 — Change types

The unit of variation

A change type is a kind of work the estate receives — interchange, clearing, authorization, network fees. It is the answer to "which passes should run, and what must be assessed regardless?" Everything a type varies lives in one directory:

core/profiles/payment_brand/change_types/interchange/
  flow.yaml                    floor · resolve · impact · release_shape
  probes.yaml                  the questions, and which passes each answer activates
  resolve_mnemonic.skill.md    the reading — how to recognise a mapping in C
  assess_qualification.skill.md a specialised reader, activated by a probe

Adding a type is a directory, not a release. No stage branches on the type — the orchestrator loads whatever the confirmed types declare. A run may confirm more than one, in which case the flows are unioned.

interchangeauthorization — the minimal second type
floorstratus.code · resolve · interface: mptstratus.code
resolvedesignator → mnemonic, via Stratus[] — no external vocabulary to translate
impact3 passes, 2 probe-activated1 pass, unconditional
release_shape§INT-4[] — no interface in play
Why the minimal second type ships on day one

authorization exists so the empty-resolve, empty-release_shape and type-union paths all execute from the first day — rather than being discovered as broken the first time a second type is genuinely needed. A declared stub is cheaper than a latent branch.

A probe earns its place with one test: does the answer change what runs? If nothing runs differently it is a note, not a probe. And there are exactly two shapes worth building — gating a specialised reader on a substance the generic arm already scans, or gating an instrument on a system nothing else touches.

# change_types/interchange/probes.yaml
probes:
  - id: INT-P1
    ask: Is this change specific to qualification criteria?
    answer_from: corpus_first        operator asked only where the documents don't settle it
    activates: [qualification_impact]   a SPECIALISED READER on stratus.code

  - id: INT-P2
    ask: Does this change pricing for existing programs?
    answer_from: corpus_first
    activates: [pricing_impact]         a different INSTRUMENT — peoplesoft.rate_tables
A "no" is a finding too

A probe answered no records its non-activation with the citation behind it — "qualification pass not run: INT-P1 answered no, sourced from mandate §4.2." Otherwise we determined this isn't qualification-related is indistinguishable from nobody considered qualification. And a probe answered unknown must never silently leave its pass unactivated: treat it as activated, the cautious direction, or escalate.

06 — The estate

What exists, and how impact crosses it

There are no API interfaces in this estate. Coupling is entirely file-based, and nothing in either side's source names the other — mpt_loader.c contains no reference to PeopleSoft and never will. So interfaces cannot be extracted; they must be declared. The flip side is that the set is small, static and enumerable, which makes declaring it cheap.

# core/estate/applications.yaml — what exists, and what each is MADE OF
- id: stratus
  in_estate: true
  acquired:  true              ← can we read its code yet?
  substances:
    - { id: code,       kind: code,        profile: c_repo.profile.yaml }
    - { id: submission, kind: file_layout, layout_at: include/submission_record.h }

- id: peoplesoft
  in_estate: true
  acquired:  false             ← declared now, repo later. NOT an error.
  substances:
    - { id: code,        kind: code }        no `profile:` — derived from acquired
    - { id: rate_tables, kind: tabular }
    - { id: mpt,         kind: file_layout }
Substance kindInstrumentWhat only it can do
codescan — full repo, code map, dependency closureeverything the code arms do
file_layoutfield diff between two declared definitionsfield-level crossing, and layout-drift detection
tabularkeyed lookup by resolved identifieroriginate an impact with no code change anywhere — a pure rate change

Crossing is mechanical, not judged. An impact promotes to an interface impact when its file:line falls inside a site declared in interfaces.yaml — reads_at, writes_at or layout_at. Then fields are derived by parsing each side's layout, and the impact crosses to every other party, in both directions.

The direction people forget

Producer changes what it writes → consumers' read sites are impacted. Consumer needs a field the interface does not carry → the producer's write site and layout are impacted. Neither is the special case — and the second cannot be found by promotion, because a field that does not exist yet has no read site to land on. Only a { interface: mpt } floor entry, assessed directly against both layouts with no code hit required, reaches it.

07 — The flow

Inside enrichment

Stage 3 is an interpreter of flow.yaml, not a fixed sequence. The order is computed, never reasoned: flow_plan.py takes the flow plus the activated pass set and returns ordered waves, refusing to return a plan at all if any declaration is malformed.

# change_types/interchange/flow.yaml
floor:                                   a MINIMUM, never a search scope
  - { application: stratus, substance: code }
  - { phase: resolve,       application: stratus }
  - { interface: mpt }

resolve:
  - id: designator_to_mnemonic
    application: stratus                 Stratus is the dictionary AND a target
    provides: [mnemonic, program_code, interchange_level]
    on_unresolved: escalate              never proceed on a partial key set

impact:
  - id: stratus_code
    needs: [mnemonic]                    identifiers, NEVER pass ids
    search:
      keys:  [mnemonic, program_code, interchange_level]   closed set, each accounted for
      scope: full_repo                                     unbounded — keys never narrow this
    reads: [v1.assertions]               on EVERY pass, without exception
needs: sequences, never scopes It decides when a pass runs and nothing more. The pass still reads every v1 assertion, searches every key, and scans the whole repo.
two search obligations keys is a closed set, each accounted for as found-here or not-found. scope: full_repo is unbounded. A pass that only searched its keys has silently become a lookup.
provides: identifiers only The schema rejects provides: [mpt_is_impacted] because that is a conclusion, not an identifier. Otherwise a pass could manufacture the agreement release_shape exists to discover.
activates: one direction only A probe names its passes; a pass never names its probes. Conditionality is derived — union every activates:, and a pass no probe names is unconditional.

08 — The spine of the output

§16 is the only route to work

Everything actionable reaches Jira through §16. It is what jira_validator traces in both directions — every §16 entry yields a story, every story traces back. A second home for impacts would mean a second spine, rebuilt from scratch.

§16.3   kind: impact          code exists — change it
        assertion: A-4  (modify_existing)
        location:  src/routing/route_table.c:88-140    [found]
        finding:   IRD 0301 rate entry — rate field set at line 112

§16.7   kind: gap             code does NOT exist — build it
        assertion: A-9  (new_capability)
        location:  src/routing/brand_registry.c:120-180    [prospective]
        basis:     IRDs 0201, 0334, 0512 are registered here
        finding:   IRD 0537 does not exist. A new registration would be added here.

§16.9   kind: verify          deliberately NOT changed — confirm why
        assertion: A-6  (modify_existing)
        location:  src/billing/fee_calc.c:210-240     [found]
        finding:   fee calculation reads the rate at runtime; no code change needed
        confirm:   that fee_calc reads rates dynamically and holds no cached copy
kindStory actionWhat code_author does
impactEDITdrafts a hunk, citing the §16 entry
gapEDIT (new build)drafts at the prospective location, or records why it cannot
verifyVERIFYnote only — never a hunk. A story saying "we deliberately did not change this" arriving with an edit attached is a contradiction
The gap case is the one that goes missing

A gap is not location-less, it is location-prospective. When the scan finds no direct landing, an analogy search locates the nearest existing instance of the same kind of thing and reports where a new one would go. "Not found" is not a story anyone can pick up; "comparable IRDs are registered here" is. Without it, the most greenfield work is the most likely to fall out of the plan entirely — a new fee program produces more gaps than impacts.

09 — The split

What is computed, and what is judged

The governing rule is mechanical recall, model precision: compute the thing whose error is invisible; let the model judge the thing a reader can check.

Computed — a scriptJudged — the model
Structural extraction — modules, edges, symbols. Frozen, never model-rewritten at runtime. purpose text on a code-map node
The run order — topological sort over provides/needs, and every load-time rejection (flow_plan.py) Whether a retrieved precedent is genuinely comparable
Promotion to an interface impact — file:line containment in a declared site How to read C source and recognise a program-name-to-mnemonic mapping
Field derivation — parsing each side's declared layout Whether an absence means a gap or a contradicted premise (given the committed assertion type)
The merge into enrichment.json — fixed-order and model-free, surfacing conflicts rather than resolving them The change draft itself, reviewed at G4
Why the sort must not be reasoned

A wrong sort is invisible. A pass started before its identifiers exist scans an empty key set, files fewer findings, and every G2 check still passes — floor totality, findings-or-non-event, all green. The only symptom is fewer §16 entries, which is indistinguishable from a change that genuinely touches less.

10 — Invariants

Rules that must not break

floor is a floor,
never a ceiling
Declared coverage is a guaranteed minimum, never a search scope. This is the one degradation somebody will later introduce as an optimisation, so it is written as a rule rather than left as an assumption.
history is a prior,
never a filter
The KB unions into scope and never subtracts. Co-change history records what people did, not what was correct — so more history makes that blind spot more confident, and the scan is the only instrument that can see what past practice missed.
silence is never
permitted
Findings, non-events ("ran, found nothing"), non-activations ("probe answered no, sourced from mandate §4.2") and boundaries ("reached PeopleSoft, repo not acquired") are all recorded. "We determined nothing is needed" must never look like "nobody looked." floor:, activates: and the declared phases supply the denominator.
join keys forward,
never conclusions
A pass may hand downstream "mnemonic X, program code Y". It may never hand down "I think MPT changes" — that would manufacture the agreement release_shape exists to discover. Enforced by restricting provides to an identifier vocabulary.
never restate a
derivable fact
A field whose value is reachable by following a declared id is a schema violation, not a convenience. No activated_by: on a pass; no acquired: on an interface party; no profile: on an unacquired substance. Every echo is a place two files drift.
absence means something
only against expectation
Every §8 assertion is typed before the code is read, and frozen in v1. Same absence, opposite verdicts: new_capability + not-found is a gap (the work); modify_existing + not-found escalates and blocks G2. Decide the type afterwards and the check rationalises every absence.
v1 + enrichment
reconstructs v2 exactly
The strongest guarantee in the system and the whole audit story — every difference between the code-blind and code-checked documents traces to a numbered finding. Parked: whether anything actually tests it. If untested it is an aspiration, not a property.

12 — Worked example

A network raises interchange on a fee program

One change, end to end. The mandate introduces a new product designator and changes rates for two existing programs. Thirteen steps, each naming the file consulted and what it produced. Steps marked KB · wave 4 depend on the historical corpus, which is proposed and gated on 003.7a — everything else runs without it.

STEP 1

The run is configured — UI_INPUT.yaml

Generate writes the run: the repo, the domain, the uploaded mandate and Tech Letter with their dispositions, and a change-type hypothesis of interchange. G0 reviews it. The hypothesis is never authoritative — Stage 2 may overturn it, and disagreement is the most valuable thing it can produce.

STEP 2

The repo becomes a map — extractor_manifest · c_repo.profile

The manifest says which frozen extractor handles C and asserts its recorded sha still matches the file on disk. The signal profile says how this repo clusters into modules and how edges are derived. Both deterministic; the model contributes only purpose text. Cached on (commit_sha, profile_sha), so a re-run is instant. This map becomes a KB layer — everything downstream queries it rather than re-deriving it.

STEP 3

v1 is authored code-blind — si_profile.payment_brand.yaml

Each of the eighteen sections is authored against its must_capture, with the routing row deciding which uploads feed it. §8 carries the business requirements as assertions — the population everything downstream is measured against — and each is typed modify_existing, new_capability or unclear before any code is read.

STEP 4
KB · wave 4

The type is confirmed — article → Jira → diffs

The KB matches v1 against past work and recommends interchange, citing precedents by Jira key — "PBI-4471 and PBI-4602 both involved IRD changes and settlement-window shifts." A recommendation the operator cannot audit is a guess wearing a justification. The operator accepts or substitutes, and decisions.jsonl records whether they differed, which is how KB quality gets measured over time. Cold start — "no similar precedent" — falls back cleanly to the Stage 0 declaration rather than blocking.

STEP 5

Probes fire, and v1 freezes — probes.yaml

  INT-P1  qualification criteria?   → NO,  sourced mandate §4.2
  INT-P2  pricing for existing?     → YES. pricing_impact turns on.

INT-P1's negative answer is recorded as a non-activation, with its citation. Then G1: v1 freezes, complete with its Change Classification section.

STEP 6
KB · wave 4

Scope opens at the floor — flow.yaml ∪ KB proposals

The floor declares what will be assessed regardless of what the scan finds — Stratus code, resolve, and the MPT interface. Then the KB unions in. The diffs from comparable past changes say which files those changes touched, so brand_registry.c enters scope even though nothing has pointed at it yet.

The KB can only widen. It never says "no comparable change touched Settlement, skip it" — history records what people did, not what was correct, and the scan is the only instrument that sees what past practice missed. And the floor is a floor, never a ceiling.

STEP 7

Resolution runs first — resolve_mnemonic.skill.md · networks.yaml

The networks publish designators; our systems key on mnemonics. Stratus is the only dictionary, so nothing else can run until this does. provides is a contract enforced before dependents start: if v1 names three designators and resolve produces zero mnemonics, the orchestrator refuses to start the passes that need them — rather than running three thin scans against an empty key set, where the failure would be invisible because the scans simply find less.

STEP 8

The impact passes run in derived order — flow_plan.py

No run order is written anywhere. The plan is computed from provides/needs, and because resolve provides everything all three passes need, all three parallelise. Each carries two obligations doing different jobs: keys is a closed set, each accounted for as found-here or not-found; scope: full_repo is unbounded, anchored to v1's assertions. Resolution creates a search obligation, not a search boundary — the failure to design against is "we resolved the mnemonics, so search for those," which silently converts the scan into a lookup.

STEP 9

Impact crosses the estate — interfaces.yaml

A Stratus impact lands on src/config/mpt_loader.c — a declared read site. It promotes at field level and crosses to every other party. Here it goes backward: Stratus needs an eligibility field MPT does not carry, so the impact reaches for PeopleSoft's write site and layout. That is a PeopleSoft code change originating from a Stratus requirement — the case nobody currently discovers until implementation. PeopleSoft is acquired: false, so what lands is a recorded boundary, not silence and not a located finding.

STEP 10
KB · wave 4

The new designator has nowhere to land — the analogy search

The mandate's new product designator resolves to no existing code. Its assertion was typed new_capability back at step 3, so this absence is expected — a gap, not an escalation. But "not found" is not a story anyone can pick up.

So the pass asks where a new one would go. The code map offers the surrounding pattern; the KB's diffs answer it outright — "when IRD 0334 was registered under PBI-4471, these three files changed." That turns a prospective location from an inference into a record, and it is where similarity is easiest rather than hardest: "the last time an IRD was registered" is a narrow, checkable class.

STEP 11
KB · wave 4

The scan is challenged — reconciliation, four quadrants

After enrichment, the engines the scan found impacted are compared against the engines the KB says comparable changes touched. Only the two off-diagonal cells reach the operator, which keeps the decision set small:

                  KB EXPECTS IT      KB NEVER SAW IT
  scan found      agreed, proceed    NOVEL — determine
  scan found none GAP — determine       not impacted

Both directions catch opposite failures. "Past interchange changes always touched clearing; you have nothing there" is under-detection. "You have stories against messaging; no comparable change ever touched it" is over-detection — and a better bloat signal than counting stories, because it names which impacts to be suspicious of.

STEP 12

Findings become the document, then the plan — jira_template

release_shape determines the release: the MPT field and its Stratus consumer must ship together — integrated, not separate — or the daily file breaks. Every pass files findings or an explicit non-event into its own file; the merge into enrichment.json is fixed-order and model-free, surfacing conflicts rather than resolving them, so v1 + enrichment still reconstructs v2 exactly. The apply pass writes §16 and the type sections. G2 accepts v2, and the epic and its stories follow.

STEP 13
KB · wave 4

The change is drafted — code_author · the precedent diff

Stage 5 reads the plan, §16 and the repo — never v2. For the gap story it also has the KB's diff for the last IRD registration, which is the strongest available grounding for what a correct change looks like in this codebase: exactly what a competent engineer does, find the last similar change and follow it.

Cited, never absorbed. The hunk carries "drafted following PBI-4471 (IRD 0334 registration)" so the human at G4 judges whether the precedent was good — because history records what people did, not what was correct, and a past diff can encode a bad pattern. Citing it makes the draft more reviewable, not less.

What the run produced

Three stories under one epic, each traceable to a §16 entry and from there to a v1 assertion: a code change in Stratus with a code_location; a rate-table update in PeopleSoft with flag: non_code, because a pure rate change touches no code anywhere; and a recorded boundary where the walk reached an unacquired system and said so. Plus one release-coordination finding: two of those must ship together.
