Data model note · Nexus Report Studio

One Ref_Num, many Epics. One Epic, many Ref_Nums.

Ref_Num is unique in KMF and unique in PBI Tracker, so the two systems join cleanly. Epics do not line up one-to-one with Ref_Nums, so the link between them needs its own table, and every report has to say what one row means. Hover any Ref_Num or Epic below to follow it through the whole page.

02

Store it as three tables, not one wide one

KMF and PBI stay at Ref_Num grain, where Ref_Num is unique. The link lives in a bridge table with one row per Ref_Num and Epic pair, tagged with which system asserted it.

KMF1 row per Ref_Num
PBI Tracker1 row per Ref_Num
Ref_Epic_Link1 row per Ref × Epic
Measures stay on the table where they are true. Financial_Impact_Estimate is a property of the Ref_Num, so it lives on the PBI row and never on the link row. That single decision is what keeps sums honest in the next step.

Flip it: the epic view

Group by Epic at pair grain and the "one epic, many Ref_Nums" case becomes a plain count. Impact is shown as a range of what the epic touches, never summed, because the same Ref_Num can sit under several epics.

05

Reconciliation becomes a set comparison

With one epic per side, drift was a single ≠. With many, each Ref_Num compares the set of epics KMF knows against the set PBI knows. This is a derived field the join job can add: CALC_Epic_Link_Status.
