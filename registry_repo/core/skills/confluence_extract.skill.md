# Confluence Extract

## Role

You turn a **staged Confluence page** (`.html` on disk, written by the connector) into
**structured, LLM-readable Markdown** under `context_set/`. You are the `confluence` lane's
equivalent of `pdf_extract` — the **first** step, feeding `doc_index`.

You extract **structure**, not meaning. You do **not** summarize.

## Why this skill lives in `core/skills/` and `pdf_extract` does not

The homing rule is that **document formats are where a domain actually shows up** — which is why
`pdf_extract` sits in the domain pack. PDF layout conventions genuinely vary by document family: a
Mastercard mandate, a Visa bulletin and an internal architecture deck are laid out differently
enough that a domain may need its own handling.

**Confluence HTML has no such variation.** It is machine-generated by one product against one DOM,
and is byte-identical in shape across every domain that uses it. Packing this skill would force
each new domain to author the same extractor again — duplication with nothing domain-specific to
absorb. So it is **referenced, not copied**, exactly like `doc_index` and `code_map_build`.

*(Design call made at TASK-127, when the first real end-to-end run found that §6.6.3's amended
per-type lanes named `confluence_extract` but nothing had ever built it — Confluence pages staged
as `.html` and stopped there, because `doc_index` requires a `.md` extract. Flagged for V.)*

## Principle — structure only, no interpretation

Identical to `pdf_extract`, and for the same reason: your output is the **retrieval substrate**.
`doc_index` segments *your* Markdown into subsections and the SI author pulls **line ranges** out of
it, so your heading hierarchy and line structure are load-bearing, not cosmetic.

- **Structural, not interpretive.** Transcribe the page's text and hierarchy faithfully: headings
  (`<h1>`–`<h6>` → `#`–`######`), paragraph order, lists (`<ul>`/`<ol>`), tables (preserve rows and
  columns as a Markdown table), and code (`<code>`/`<pre>` → backticks or a fenced block).
- **Wrap prose at `extract_wrap_columns`** (`core/retrieval_config.yaml`, default 100). The **line**
  is the unit the index selects in and the author pulls by, so an unwrapped 200-word paragraph makes
  every line range degenerate.
- **No summarization.** The index pass summarizes; you preserve. A downstream summarizer cannot
  recover detail you dropped.
- **No classification.** You do not decide what the page is *for* — that is the operator's
  `disposition` (D-A12), declared in `UI_INPUT` and carried onto the entry by `source_processor`,
  never inferred from content.
- **Drop chrome, keep content.** Navigation, breadcrumbs, the Confluence byline/footer, edit links
  and macro scaffolding are **not** page content. Removing them is structural, not interpretive —
  but never drop something merely because it looks unimportant.
- **HTML comments are not content.** A staged fixture may carry authoring notes in `<!-- -->`;
  those describe the file, not the page.
- **Cite-or-flag fidelity.** Transcribe what is on the page; never fabricate. If a region cannot be
  transcribed (an unrendered macro, an embedded image with no alt text), record a
  `[[unreadable: <where>]]` marker rather than guessing — the honesty floor everything downstream
  depends on.
- **Domain-agnostic by nature.** It does not branch on `domain` (D7).

## Input

One staged `.html` file, given as an on-disk path by `source_processor`, plus the connector
descriptor (`source`, `url`, `staged_path`, `auth_ref`, `ingest_ts` — §6.6.2).

## Output

1. **`context_set/<source>/<page>.md`** — the structural extract. Title from `<h1>` (falling back to
   `<title>`) as the document's `#` heading.
2. **A manifest-entry stub** (§3.2) for `merge_manifest.py`: `path`, `source`, `type`, `url`,
   `ingest_ts`, `disposition` (carried from `UI_INPUT`, never inferred), `lines_total`.
   `index_path` is filled by the `doc_index` pass that follows, not by you.

## Procedure

1. Read the staged `.html`.
2. Strip comments and non-content chrome (`<head>` except `<title>`, nav, footer, byline).
3. Walk the body **in document order**, mapping each element to its Markdown equivalent. Preserve
   sibling order exactly — the reader's path through the page is part of its structure.
4. Wrap prose to `extract_wrap_columns`. Never wrap inside a table row or a fenced block.
5. Write the `.md` beside the staged `.html`, and return the entry stub with `lines_total` set to
   the extract's line count.

## Boundaries

- You never fetch — the connector already staged the page.
- You never write `<page>.index.json`; that is `doc_index`'s output.
- You never assign a disposition, and you never edit the staged `.html`.
