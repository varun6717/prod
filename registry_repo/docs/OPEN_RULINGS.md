## 1. Where `confluence_extract` lives — `core/skills/` or the domain pack

**What.** I built `confluence_extract` (the lane §6.6.3 named and nobody implemented) and put it in
`core/skills/`, *not* `core/profiles/<domain>/adapter/` where its sibling `pdf_extract` sits.

**Why it's yours.** It is a seam decision, and the homing rule is in the spec: *"document formats
are where a domain actually shows up."* I judged that rule doesn't reach Confluence and acted on
that judgment without asking.

**My reasoning.** PDF layout conventions genuinely vary by document family — a Mastercard mandate, a
Visa bulletin and an internal architecture deck are laid out differently enough that a domain may
need its own handling. Confluence HTML has no such variation: it is machine-generated by one product
against one DOM and is identical across every domain. Packing it would make every new domain
duplicate the same extractor with nothing domain-specific to absorb.

| Option | Consequence |
|---|---|
| **A. Leave it in `core/skills/` (recommended)** | one extractor for all domains; consistent with `doc_index` and `code_map_build`, which are referenced not copied |
| B. Move it to the domain pack | symmetry with `pdf_extract`; every new domain re-authors an identical file |

**Recommendation: A.** If you disagree it is a file move plus one line in `adapter.yaml` —
`verify_confluence` asserts the current home, so it will fail loudly and tell you what to change.

## 2. G3's score gates structurally but never binds

**What.** All three gates compute `eligible = score_pass and hard_ok`, so the score *is* a gate. But
a plan with an **orphan epic** — a structurally broken plan — scored **91/85**. It passed the score
and was refused only by the hard checks.

**Why it's yours.** Whether the score is *meant* to carry weight at G3 is a design intent question.
The mechanism works; the calibration may not.

| Option | Consequence |
|---|---|
| **A. Accept it — at G3 the hard checks are the gate (recommended)** | honest and already true. G3 asks "is this plan pushable", which is a structural question, not a graded one. Document that the score is informational here |
| B. Sharpen the scoring so structural damage costs score | more work, and it duplicates what the hard checks already decide absolutely |
| C. Drop the score at G3 entirely | loses the trend signal across runs (M09 reads it) |

**Recommendation: A**, with one line added to §9.4 saying so. The thing to avoid is leaving a
number that looks like it protects something and doesn't — G1 and G2's scores *do* bind (G1 failed
at 80/85 in the acceptance run before citations were completed), so a reader reasonably assumes G3's
does too.

## 3. The G2 §9.3 formula amendment is mine and unreviewed

**What.** §9.3's provisional `impact_coverage` scored a **complete, correct run at 0.417** because 7
of 12 requirements were fully analysed and found to need *no change* — they had no §16 entry and no
disposition, and the literal reading counted that as a gap. Worse, it made **manufacturing §16
entries the cheapest way to pass**. I amended it in-task to count a requirement as covered when Arm 1
reached it, whatever the verdict.

**Why it's yours.** It changes a pinned gate threshold. D-A23 asked for the provisional formula to be
evaluated against a real run before freezing — that evaluation happened, but the *replacement* has
only ever scored 100 and has never been shown to fail anything.

| Option | Consequence |
|---|---|
| **A. Ratify the amendment as it stands (recommended)** | the failure mode it fixes is real and was demonstrated; the port note is already in `TECH_SPEC.md` |
| B. Ratify but require a discriminating case first | stronger, and cheap — seed a run where Arm 1 misses requirements and confirm the score drops |
| C. Revert to the provisional formula | reinstates a metric that rewards manufacturing impacts |

**Recommendation: B, then A.** The amendment is right, but "has only ever scored 100" is exactly the
property I flagged in the original formula. It deserves the same test I applied to its predecessor.

## 4. `pdf_extract` owns the entry `descriptor`

**What.** The manifest entry's `descriptor` — the one-line identification the SI author reads when
choosing sources — is written by `pdf_extract`, the *format* step, rather than `doc_index`, the
*understanding* step.

**Why it's yours.** It is a responsibility boundary between two skills, and it now differs per lane:
`confluence_extract` and the Jira connector must each produce their own descriptor, so the same
field is authored in three places.

| Option | Consequence |
|---|---|
| **A. Move `descriptor` to `doc_index` (recommended)** | one author for one field, on the step that already reads the whole document to summarise it. Extract steps stay purely structural, which is what their own principle section claims they are |
| B. Leave it with the extract steps | no work; three implementations of one field, and each new source type adds a fourth |

**Recommendation: A**, but **not urgent** — it is a tidiness fix, and the current arrangement
produces correct descriptors today. Worth doing before a second domain, not before the port.

## 5. Two D-A18 example divergences in ADR-008

**What.** ADR-008's illustrative index example (lines 1038–1039) disagrees with the built contract in
two places:

- `"disposition": "business_requirement"` — a **string**, where D-A12 makes disposition always a
  **list** (`["business_requirement"]`), which is what `merge_manifest` enforces and what the built
  indexes carry.
- `"pages": 40` — a field the normative output shape does not include and nothing produces.

**Why it's yours.** The ADR is normative for the pivot subsystems. An example that contradicts the
contract is a trap for whoever implements from it next — most likely at port time.

| Option | Consequence |
|---|---|
| **A. Correct the example to match the built contract (recommended)** | the ADR stops contradicting itself; carry the fix into the JPMC-side copy |
| B. Change the contract to match the example | wrong direction — the list form is load-bearing (D-A12 multi-disposition) and `pages` has no consumer |
| C. Leave it, annotate as illustrative | the divergence survives the port |

**Recommendation: A.** Two-line edit plus a port note. It is the cheapest item on this list and the
one most likely to cost someone an afternoon.

## 6. G1: a declared gap costs score but does not block

**What.** An honest `[TBD — unsourced]` lowers `section_coverage` (so it costs score) but does not
fail any hard precondition, provided it is declared in §17. In the acceptance run three such gaps
left the score at 0.967 rather than 1.000.

**Why it's yours.** It is the calibration of the honesty incentive, and it cuts both ways.

| Option | Consequence |
|---|---|
| **A. Keep it (recommended)** | declaring a gap is cheaper than hiding one, which is the incentive you want, while still applying pressure to close it |
| B. Make declared gaps free | removes all pressure; a document of pure `[TBD]`s could score 100 |
| C. Make them blocking | punishes honesty — an author who cannot source something would be pushed to invent, which is precisely what cite-or-flag exists to stop |

**Recommendation: A.** Confirming it as intentional is worth doing explicitly, because it looks like
an oversight until you see the alternatives.

## 7. `ingest_jira._flatten` renders list fields as paragraphs

**What.** Jira list fields (`labels`, `components`, `fixVersions`) render as blank-line-separated
paragraphs rather than a Markdown bullet list, so `labels: [payment-brand, discover, routing]`
becomes three paragraphs.

**Why it's yours.** Totality holds and nothing is lost, so it is a quality call, not a defect. But it
inflates the line count the index selects in — three lines of content occupy eight.

**Recommendation: fix it** (render lists as bullets — a few lines in `_flatten`), but **after** the
port. It has no correctness consequence and the Jira lane is not on the critical path.

## 8. The "unaided operator" acceptance claim is not attested

**What.** TASK-127's acceptance condition reads *"an operator completes the fresh run unaided through
UI + tool."* Every gate in the run **was** an operator act, but performed by you in conversation
rather than through a UI affordance. I cannot attest a usability claim about a human.

**Why it's yours.** Only you can say whether the condition is met.

| Option | Consequence |
|---|---|
| **A. Attest it on the VDI run instead (recommended)** | the VDI run is the real operator path with real sources; that is where the claim belongs |
| B. Re-run here with you driving the UI unaided | attests it in the external build, where the UI is not the one operators will use |
| C. Weaken the condition to "every gate is an operator act" | accurate to what was proven, but drops a real requirement rather than deferring it |

**Recommendation: A.** `ACCEPTANCE_SI.md` already records the limitation explicitly, so nothing is
being claimed that was not shown.
