Interchange level codes · management brief

Two processes are picking from one mnemonic pool. Give them one generator.

Every interchange change, custom or published, needs new mnemonics (interchange level codes) and their interchange level names. Custom Interchange picks them with automation. Published Interchange picks them by hand. Nothing stops both from picking the same one.

Proposal: one Interchange Code Generator, reached through an API by the automation and through a UI by Product Owners
Scope Mastercard first, matching the current Custom Interchange automation Source of truth PeopleSoft boarding system Unchanged Mod1 / Mod2 downstream process

Today

Two hands, one pool, no coordination

Both paths read PeopleSoft to see which mnemonics are already in production. Neither path reserves what it chooses, and neither can see what the other is about to choose.

Path A Custom Interchange, automated

Built end to end, Mastercard first. Reads production mnemonics from PeopleSoft, selects available codes with an AI plus deterministic Python approach, generates the level names, and attaches the MOD1 / MOD2 file to the epic.

Path B Published Interchange, manual

Product managers run the same steps by hand: look up what is in production, choose mnemonics, write names, type the MOD file. Slow, and invisible to Path A.

The gap No reservation step

PeopleSoft only shows what is already in production. A mnemonic chosen last week for an epic still in flight looks free to everyone else.

WHY IT MATTERS

Two epics can leave pre-discovery carrying the same interchange level code. Each side has already written a MOD1 / MOD2 file around it.

The collision surfaces late, at boarding, when it is most expensive to unwind: one epic re-codes, its MOD files are redone, and the downstream Mod1 / Mod2 work restarts.

Recommended

One Interchange Code Generator, two doors

A central engine owns the official Available Pool. The Custom Interchange automation reaches it through an API, exactly the way it calls the generator logic today, and uses Mode 1 only. Product Owners reach it through a UI during pre-discovery and can use Mode 1 or Mode 2. Every pick leaves the pool the moment it is made.

The two modes

Start from the article, or start from a number

Both modes end in the same place: a list of free mnemonics and names, reserved to this epic.

Both doors

The same AI plus deterministic Python approach the Custom Interchange automation already runs, now offered to Product Owners as a button. Open to both doors. The automation uses this mode, and only this mode, over the API.

MODE 2

Product Owner only

→

For the Product Owner who already knows the shape of the change. Product Owner only, through the UI. No PeopleSoft lookup by hand: the engine does the availability check.

One request, end to end

What a Product Owner does in pre-discovery

1

Open the generator and pick the epic Product Owner

The request is tied to a Jira epic from the start, so every code reserved later has an owner.

2

Choose a mode Product Owner

Paste the article, or enter a count with qualification criteria per mnemonic.

3

The engine checks availability Engine

Backend API calls establish which candidates are already in production in PeopleSoft and which are already reserved by another epic. Only free codes come back.

4

Select, and the codes leave the pool Product Owner · Engine

The chosen mnemonics are removed from the official Available Pool with their generated interchange level names. Nobody else can pick them now.

5

MOD1 / MOD2 file lands on the epic Engine

A file with interchange code and interchange name is generated and attached to the Jira epic, the same artifact the automation produces today.

6

Downstream Mod1 / Mod2 process picks it up Unchanged

Still manual today. It receives the same file it always has, now guaranteed not to collide with anything in flight.

Automation path The Custom Interchange program enters at step 2 with Mode 1 only. It calls the same Interchange Code Generator over API, as its current code already does, passes the article, receives the level codes and names, and attaches the MOD1 / MOD2 file to its epic. Its process does not change. Its picks now come out of the same pool as everyone else's.

Why this is the right cut

Removes the risk by construction, reuses what is built

Risk Overlap becomes impossible

A code can only be handed out once, because there is only one pool and every pick leaves it. No process rule to remember, no second check at boarding.

Reuse The engine already exists

The article-to-mnemonic logic and the name generation are the Custom Interchange automation's, wrapped in a UI. The automation keeps calling it the same way.

People Product Owners stop trawling PeopleSoft

Pre-discovery gets a button instead of a lookup. Suggested names come with the codes, and the MOD file is written for them.

Blast radius Downstream is untouched

Mod1 / Mod2 stays manual and receives the same file. Nothing after the epic has to change to get the benefit.
