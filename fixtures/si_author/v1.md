# Solution Intent — Mastercard MCS-2026-R3 Brand Mandate

**Initiative level:** PBI change · **Application:** MerchantRoutingSvc · **Status:** v1 (pre-G1)

## 1. Executive summary

Mastercard has issued brand mandate **MCS-2026-R3**, binding on all Mastercard-licensed acquirers
including JPMC Merchant Services, with full compliance required by **2026-09-30**
[src: context_set/sharepoint/mastercard_mandate_part1_2026.md L15–31]. The Merchant Routing
Service must carry MDES token data end-to-end on the authorization message, route token traffic
exclusively through the Banknet MDES gateway, populate the new token assurance element so eligible
transactions qualify for the reduced interchange tier, and extend three downstream reports [frame].

The mandate arrives in two parts: Part 1 states the obligation, brand rules and certification
gates; Part 2 (MCS-2026-R3-T) carries the normative technical detail and takes effect on the
Mastercard network on **2026-07-01**, ahead of the acquirer compliance date
[src: context_set/sharepoint/mastercard_mandate_part2_2026.md L16–22].

Delivery is five deliverables (§7) carrying twelve requirements (§8): the authorization message
layer, Banknet routing, interchange qualification, downstream reporting, and a MAC Level 2
certification package.

**The item not to miss:** certification is not a formality with a soft edge. An acquirer that has
not achieved MAC Level 2 by 2026-09-30 has **all** Mastercard and Maestro transactions
automatically downgraded to the Standard non-qualified interchange tier and is placed on a 90-day
remediation plan [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L114–118]. The
commercial exposure is therefore the entire Mastercard portfolio, not the token subset.

## 2. Problem statement

Today the Merchant Routing Service identifies a card brand by **PAN BIN-range lookup at
authorization time**, then dispatches the message to a brand-specific handler (`mc_handler`,
`visa_handler`, `discover_handler`). Routing is table-driven and reloadable without a deploy
[src: context_set/confluence/discover_routing_kb.md L7–17]. The message layer uses ISO 8583 (1987)
with brand-specific field 48 usage for Mastercard, with field-level mappings held in a format
registry [src: context_set/confluence/message_format_kb.md L6–10].

That current state cannot satisfy MCS-2026-R3 in four concrete ways:

- **No token data path.** The mandate requires DE 48.66 (Token Requestor ID), DE 48.77 (Digital
  Wallet Indicator) and DE 48.78 (Token Assurance Level) on authorization and financial request
  messages; today's field 48 usage predates them
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36].
- **BIN-range brand resolution does not distinguish token traffic.** MDES token BINs 520000–529999
  must route exclusively to the Banknet MDES gateway (MCB-MDES-01); any path that bypasses it hard-
  declines with Response Code 58
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L92–99].
- **Interchange qualification has no token input.** The reduced "Token Enhanced" rate applies only
  when DE 48.78 carries an assurance level of 50 or above; failing to populate it forces Standard
  rate assessment, and retroactive adjustments are not processed
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L48–70].
- **Reporting predates the new fields.** The Daily Settlement Report, the Regulation II quarterly
  filing and a new monthly MDES coverage report all require data the service does not currently
  emit [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L102–128].

The parties affected are acquiring merchants (through interchange cost and decline behaviour),
Settlement Ops (through the DSR format change) and Brand Compliance (through certification and the
Regulation II filing) [frame].

**What it costs today: [TBD — unsourced].** Neither mandate part nor the KB pages state current
token-transaction volume, current interchange paid, or a defect or dispute rate for the existing
brand-resolution mechanism. Recorded as an open question (§17) rather than estimated.

## 6. High-level use case

**U1 — Token-bearing authorization, end to end.** The mandate changes an existing flow rather than
introducing a new one; the flow below is today's, with the mandated changes marked.

1. Authorization request arrives at the Merchant Routing Service
   [src: context_set/confluence/discover_routing_kb.md L18–22].
2. Brand resolution from the PAN BIN range
   [src: context_set/confluence/discover_routing_kb.md L7–11]. **Changed:** token BINs
   520000–529999 must now be recognised as MDES token traffic
   [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L92–99].
3. Handler dispatch to the brand handler
   [src: context_set/confluence/discover_routing_kb.md L12–17]. **Changed:** endpoint selection
   resolves against Mastercard BIN Table v2026-Q2 and must be immutable once made
   [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82]; token traffic goes
   exclusively to MCB-MDES-01
   [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L92–99].
4. Response normalization
   [src: context_set/confluence/discover_routing_kb.md L18–22]. **Changed:** Response Code 55 on a
   token transaction now means "Token Assurance Level insufficient", not "Incorrect PIN"
   [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L82–90].
5. Ledger write [src: context_set/confluence/discover_routing_kb.md L18–22]. **Changed:** the
   selected network ID and routing reason code must reach the audit record within 200ms
   [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82].

**Failure paths.** A brand handler being unavailable applies a configured fallback and records
`EBRAND_UNAVAILABLE` with bounded retries
[src: context_set/confluence/discover_routing_kb.md L23–26]. A primary Banknet endpoint not
responding within 4000ms may fall back to the secondary, logged with reason code T, and on
secondary timeout must forward to STIP rather than declining at the acquiring host
[src: context_set/sharepoint/mastercard_mandate_part1_2026.md L73–81].

**U2 — Interchange qualification**, **U3 — Reporting** and **U4 — Certification** are supporting
use cases covered by §8 R7, R11 and R12 respectively.

## 8. Business requirements

#### R1 — MDES token integrity preserved end to end
**Deliverable:** D1
**Description:** Token values and their associated identifiers must survive the full authorization
chain unmodified, because de-tokenization is the network's responsibility and not the acquirer's.

**Assertions:**
- R1.1 — MDES tokens are not de-tokenized before the authorization request is forwarded to Banknet [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L51–64]
- R1.2 — Token values are neither stripped nor substituted anywhere in the acquirer path [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L51–64]
- R1.3 — The Token Requestor ID in DE 48.66 is preserved through the full authorization chain [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L51–64]

#### R2 — New authorization data elements populated
**Deliverable:** D1
**Description:** The four new field 48 subelements must be present with correct type, length and
presence conditions on authorization and financial request messages.

**Assertions:**
- R2.1 — DE 48.66 Token Requestor ID (N-11) is populated when DE 2 is an MDES token BIN 520000–529999 [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36]
- R2.2 — DE 48.77 Digital Wallet Indicator (AN-2, values 01–05) is populated when the payment originated from a digital wallet [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36]
- R2.3 — DE 48.78 Token Assurance Level (N-2, 00–99) is populated when DE 2 is an MDES token [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36]
- R2.4 — DE 48.79 Device Type (AN-2) is populated where known; it is optional [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36]
- R2.5 — These elements apply to MTI 0100/0110 and 0200/0210 messages from 2026-07-01 [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36]

#### R3 — Modified data elements accepted and emitted
**Deliverable:** D1
**Description:** Four existing elements change shape or scope and the service must not reject the
new forms.

**Assertions:**
- R3.1 — DE 61.8 bit 3 value '3' (Soft POS) is accepted and not rejected [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L37–45]
- R3.2 — DE 104 accepts up to 40 bytes in UTF-8, truncating on byte boundaries rather than characters [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L37–45]
- R3.3 — DE 55 carries EMV tag 9F6E for contactless transactions above USD 50 [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L37–45]
- R3.4 — DE 48.10 is populated on Maestro transactions in the EU/EEA region [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L37–45]

#### R4 — Banknet endpoint selection is deterministic and auditable
**Deliverable:** D2
**Description:** Endpoint selection must follow the BIN-first lookup and be immutable once made.

**Assertions:**
- R4.1 — The 6-digit BIN is extracted from DE 2 and resolved against Mastercard BIN Table v2026-Q2 [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82]
- R4.2 — The Banknet endpoint is selected from product type and Regulation II routing preference [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82]
- R4.3 — A routing decision is immutable once made, except on a documented primary-endpoint timeout of 4000ms or more [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82]
- R4.4 — The selected network ID and reason code are written to the transaction audit record within 200ms of the decision [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82]

#### R5 — Regulation II debit routing obligations met
**Deliverable:** D2
**Description:** US Debit Mastercard and Maestro routing must satisfy 12 CFR Part 235.

**Assertions:**
- R5.1 — At least two unaffiliated networks are available for PIN debit [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L83–91]
- R5.2 — Routing selection evaluates merchant preference, then issuer preference, then cost optimization, in that priority order [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L83–91]
- R5.3 — No routing exclusivity arrangement limiting merchant choice is implemented [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L83–91]
- R5.4 — The routing decision rationale is retained in the audit ledger for at least three years [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L83–91]

#### R6 — MDES token traffic routes exclusively to the MDES gateway
**Deliverable:** D2
**Description:** Token BIN transactions have exactly one legal path.

**Assertions:**
- R6.1 — Transactions with DE 2 in BIN range 520000–529999 route to endpoint MCB-MDES-01 [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L92–99]
- R6.2 — Token transactions are never routed to acquirer-side processing or an alternate debit network [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L92–99]

#### R7 — Interchange qualification reflects token assurance
**Deliverable:** D3
**Description:** Eligible token transactions must reach the reduced Token Enhanced tier.

**Assertions:**
- R7.1 — DE 48.78 is populated wherever a token assurance level is available [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L48–70]
- R7.2 — Transactions with DE 48.78 of 50 or above are qualified at the Token Enhanced rate [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L48–70]
- R7.3 — Qualification logic applies from the network effective date 2026-07-01 [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L48–70]

#### R8 — Contactless cardholder verification conforms
**Deliverable:** D1
**Description:** Contactless transactions above the CVM threshold must request and carry a CVM result.

**Assertions:**
- R8.1 — Contactless transactions above USD 100.00 request CVM results per EMV Contactless Kernel C-3 [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L65–72]
- R8.2 — CVM methods are attempted in the order Online PIN, Offline Enciphered PIN, Signature [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L65–72]
- R8.3 — No-CVM is permitted only for MCCs 4111, 4121, 4131 and 7523 [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L65–72]
- R8.4 — The CVM result is carried in DE 55 tag 9F34 [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L65–72]

#### R9 — Authorization timeout and stand-in fallback
**Deliverable:** D2
**Description:** Timeout handling must prefer stand-in processing over an acquirer-host decline.

**Assertions:**
- R9.1 — A primary Banknet endpoint not responding within 4000ms may be retried against the secondary endpoint [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L73–81]
- R9.2 — A fallback attempt is logged with reason code T in the transaction audit record [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L73–81]
- R9.3 — On secondary-endpoint timeout the authorization is forwarded to STIP rather than declined at the acquiring host [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L73–81]

#### R10 — Decline reason code semantics updated
**Deliverable:** D1
**Description:** Response Code 55 changes meaning for token transactions and merchant-facing
messaging must follow.

**Assertions:**
- R10.1 — Response Code 55 on a token transaction is interpreted as "Token Assurance Level insufficient", not "Incorrect PIN" [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L82–90]
- R10.2 — Token transactions are identified for this purpose by BIN range 520000–529999 [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L82–90]
- R10.3 — Merchant-facing decline messaging for this case reads "Unable to process — please retry with chip card" [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L82–90]

#### R11 — Downstream reporting obligations discharged
**Deliverable:** D4
**Description:** Three reports change or are introduced, each with its own format and cadence.

**Assertions:**
- R11.1 — The DSR Product Code field is extended from 2 to 4 characters using MBT v2026-Q2 codes [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L102–110]
- R11.2 — The DSR carries a Token Flag column derived from DE 48.77 presence [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L102–110]
- R11.3 — The DSR includes a wallet-type breakdown reporting DE 48.77 codes 01–05 separately when token transactions are present [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L102–110]
- R11.4 — The Regulation II quarterly report carries transaction count and interchange by network, routing override count with justification codes, and a CCO certification statement [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L111–119]
- R11.5 — The monthly MDES coverage report carries total and token transaction counts, assurance-level distribution in buckets 0–9/10–49/50–99, and DE 48.66 TRID population rate [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L120–128]

#### R12 — MAC Level 2 certification achieved
**Deliverable:** D5
**Description:** Certification is a precondition of continued qualified interchange, not a
post-delivery formality.

**Assertions:**
- R12.1 — Gate C1 passes 100% of Category A and 85% of Category B Mastercard Test Suite v8.4 cases [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L98–113]
- R12.2 — Gate C2 submits 1,000 end-to-end traces including at least 300 MDES token, 100 fallback chip and 50 Regulation II debit samples [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L98–113]
- R12.3 — Gate C3 sustains the 60-day production monitoring period without an unremediated alert-threshold breach [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L98–113]
- R12.4 — MAC Level 2 is held by 2026-09-30 [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L114–118]

## 10. Constraints & design principles

**Hard technical constraints**

- ISO 8583 field 48 subelement structure and the stated type/length of each new element — N-11,
  AN-2, N-2, AN-2 respectively [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L25–36].
- DE 104 capacity of 40 **bytes** in UTF-8; truncation must not split a multi-byte sequence
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L37–45].
- Primary-endpoint timeout threshold of 4000ms as the only condition permitting re-routing
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82].
- Audit-record write within 200ms of the routing decision
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82].
- Regulation II audit retention of at least three years
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L83–91].

**Design principles**

- **Routing decisions are immutable once made** — mid-transaction re-routing is prohibited outside
  the documented timeout case [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L73–82].
- **No bypass of the MDES gateway** for token BIN ranges, on pain of a hard RC 58 decline
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L92–99].
- **De-tokenization is the network's, not the acquirer's**
  [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L51–64].
- **Brand rules are enforced at the format layer before dispatch**, which is where the existing
  service already places them [src: context_set/confluence/message_format_kb.md L11–14].

**Dates constraining how, not only when**

- Network effective date **2026-07-01**: transactions processed on or after this date must comply,
  which precedes the acquirer compliance deadline and therefore constrains sequencing
  [src: context_set/sharepoint/mastercard_mandate_part2_2026.md L129–136].

## 12. Out of scope

- **Visa and Discover brand handling.** MCS-2026-R3 binds Mastercard-branded traffic only; the
  existing `visa_handler` and `discover_handler` paths are untouched
  [src: context_set/confluence/discover_routing_kb.md L12–17].
- **Prepaid Mastercard MDES token support.** Prepaid products are explicitly excluded from the MDES
  token requirements, though they remain subject to the interchange and routing changes — so they
  are partially in scope and this exclusion is narrow
  [src: context_set/sharepoint/mastercard_mandate_part1_2026.md L32–48].
