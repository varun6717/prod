LAYER 01 Payment brand articles Network mandates and technical letters — the external world, in the networks' own vocabulary. They name the programs and the target rates; they know nothing about our systems.
LAYER 02 Payment system flows How our estate is wired: which system feeds which, over which file, on what cadence. This is what lets impact cross from one system to another.
LAYER 03 Change history KB Every past change, joined to the stories raised for it and the code that actually shipped. The institutional memory, made queryable.
LAYER 04 Code map Modules, dependencies and interface points, derived mechanically from the source — never guessed, never hand-maintained.
LAYER 05 System code & data Stratus code, read in full on every run rather than sampled — and PeopleSoft's rate tables, which hold the current rate for every mnemonic. A pure rate change touches no code at all, and is visible only here.
A service, not a folder

The knowledge base runs as its own application and is reached over MCP — the same way the agent reaches any tool. Layers can be re-indexed, corrected or added without the pipeline changing, and every query it answers is logged like any other call.

Grounded, not guessed

Every claim the system makes traces to a source: a line in the mandate, a declared interface, a past Jira key, or a file and line number in the code. Anything it cannot ground, it marks as unsourced rather than inventing.

Nothing goes quiet

A check that finds nothing says so. A step that did not run records why. “We looked and it is clean” is never allowed to look like “nobody looked.”

A person decides

Five gates, one per stage. The system proposes and evidences; approval is human at every step, and both writes that leave the building sit behind one.

One change, end to end

A network raises interchange on a fee program: a new product designator, and rate changes for two existing programs. Thirteen steps — and each one names which layer of the knowledge base it draws on.

What kind of change is this? STAGE 2 · KB classification → decisions.jsonl — TASK 003.8 The history layer matches this article against past work and recommends interchange — citing the past Jira issues it based that on. A person accepts or overrules, and the system records which. A recommendation nobody can audit is a guess wearing a justification.

Is it about qualification criteria? No, per mandate §4.2. The "no" is recorded with its citation, so "we checked" never looks like "nobody asked." The requirements document is then frozen.
STAGE 3Enrichment→ G2 · v2 accepted

Where should we look? STAGE 3 · scope opens = flow.yaml floor ∪ KB proposals A guaranteed minimum is assessed no matter what. Then history widens it: the actual code changes from comparable past work say which files were touched last time, and those enter scope too. History can only ever widen — it never rules anything out, because it records what people did, not what was correct.

Translate the network's language into ours STAGE 3 · resolve → resolve_mnemonic.skill.md → provides: [mnemonic] Card networks publish program names. Our systems key on internal mnemonics. Stratus is the only place that mapping exists, so nothing else can run until it is done — and if it comes back empty, the run stops rather than searching for nothing.
08
system code & data
Find everywhere it lands STAGE 3 · impact → stratus_code · pricing_impact → §16 The whole repository is read, not sampled, anchored to the frozen requirements. Rate tables are checked separately — a pure rate change touches no code anywhere and would otherwise be invisible.

payment system flows
The impact crosses into another system STAGE 3 · cross → interfaces.yaml → recorded boundary Stratus needs an eligibility flag the daily merchant file does not carry — so the impact reaches back to PeopleSoft, which produces that file. A PeopleSoft change originating from a Stratus requirement: the case nobody currently discovers until implementation. That repo is not yet available, so it is recorded as a known boundary rather than passed over.

The new designator has nowhere to land STAGE 3 · kind: gap → analogy search → location: prospective It was declared as new back at step 3, so finding nothing is expected — this is the work, not a failure. But "not found" is not something anyone can pick up. History answers it: "when the last designator was registered, these three files changed." A location by record rather than by inference.

change history kb
The result is challenged STAGE 3 · reconciliation → four quadrants — TASK 003.9 What the scan found is compared against what comparable past changes touched. Agreement passes silently; only disagreements reach a person — "past changes always touched clearing and you have nothing there", or "you have work against a system no comparable change ever touched." Both directions, both worth a human minute.

→ the plan
Findings become the plan release_shape → enrichment.json → v2 → G2 → STAGE 4 jira_author One epic for the article, with a story per finding. The system also states what must ship together: the merchant-file field and the Stratus code that reads it, or the nightly batch breaks. Today nobody learns that until implementation. A person accepts before anything reaches Jira.
STAGE 5Code change→ G4 · push to branch
13
system code & data
The change is drafted STAGE 5 · /start-code → code_author → code_changes/ → G4 Reviewable diffs, each citing the finding that justifies it — and for the new designator, following the shape of the last comparable change, cited by its Jira key so a reviewer can judge whether that precedent was a good one. A person approves before anything reaches a branch.

What the run produced: one epic, three stories — a code change in Stratus, a rate-table update in PeopleSoft that touches no code at all, and a recorded boundary where the analysis reached a system we cannot yet read and said so. Plus one release constraint: two of those must ship together. Every one of them traces back to a line in the mandate.
