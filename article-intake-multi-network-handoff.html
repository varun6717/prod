Extraction and validation loop

§3a

Vision mode because the 16 networks vary widely in layout, tables and scan quality. Volumes are low, so the extra cost and latency are acceptable.

01

Render to images. Every upload (PDF, Word, HTML, scan) becomes page images. Keep the text layer where one exists.

02

Vision extraction (primary). Model reads the page images in their source language and fills the core fields. Few-shot examples come from that network's historical SharePoint records.

03

Text cross-check. Compare exact values (dates, titles) against the original-language text layer. Disagreements get flagged. For French networks, translate title and description to English after this step (see §3c).

04

Deterministic rule checks. Cheap, run before the validator:

Effective date ≥ publish date
Region is in the fixed list
Impact ∈ {issuer, acquirer, both}
All required fields present
05

Recursive validation agent. Gets the extraction plus the page images, confirms or corrects each field. Different prompt, ideally a different model, so the extractor is not grading its own work.

06

Loop cap and scoring. Stop after 2–3 validation passes. Score each field, then the record: validator agreement, text cross-check match, and rule-check results feed a 0–1 probability. Any hard failure or a score under the threshold sets high risk.

Exit gate · review on everything Every record → human review queue with its confidence score and flagged fields. Nothing loads until a reviewer clears it. High risk (score below threshold, any rule failure, or loop hit the cap) → flagged and moved to the front of the queue. Reviewer clears → load to SharePoint, tagged with the network identifier, score and flag stored with the record.

Prompt assembly and retrieval

§3b

One shared base prompt, one config file per network, similar past articles injected at runtime. The network tag from the MFTS upload drives assembly.

base_prompt (1 file)
Shared extraction instructions, field definitions, output schema, and a slot for retrieved examples.
+
networks/<tag>.config (1 per network)
Network-specific rules, terminology, layout quirks, field-mapping notes, and language (drives the translation step). Tuned and version-tracked independently.
+
retrieved examples (top 5)
Past SharePoint records for the same network, each with all fields filled in.

Retrieval, two passes

quickPull title and description from the article. Non-English networks: translate that pair to English right here, since the history it is matched against is English.
retrieveSearch that network's historical SharePoint records (all English) by title + description similarity. Keep the top 5.
fullRun full extraction with those 5 records as few-shot examples. Output feeds the validation loop.
fallbackNetwork has too few records → add similar examples from other networks.

Knowledge base

SharePoint already holds years of article loads across all networks, in English. Use it for few-shot examples per network, to learn historical field mappings, and to build a labeled evaluation set so accuracy is measured per network before go-live.

Non-English networks (e.g. French): where translation goes

§3c · decision

Translate after extraction, inside stage 4, never before it. The vision model reads French page images directly and fills the schema. Dates, region and impact are language-independent once normalized. Only the free-text fields (title, description) need an English version, and both languages travel together through validation and review.

chosen · last step of stage 4
Extract every field in the source language → normalize structured fields (« 1er mars 2026 » → ISO date, region and impact to the fixed English lists) → translate title and description to English → pass original + English into the validation loop. (The quick pass also makes a throwaway English pair earlier, just for retrieval.) Language comes from the network config (language: fr); detect as a fallback for bilingual networks.
vs
rejected · translate the document first
Machine-translating the PDF before extraction breaks the layout and tables vision mode depends on, adds a lossy step before the one that matters, and the text cross-check would then compare against translated text instead of the source.
vs
rejected · translate at load time
Validator and reviewer would see French free-text with nothing to check the English against, retrieval against English history would not match, and SharePoint would receive an unvalidated translation.

How it ties into the rest of the flow

retrieveThe retrieval corpus (SharePoint history) is English for every network. So the quick pass translates title and description to English first and searches with that pair. This is the one translation that happens before extraction; it is only used to find examples, never stored as the final value.
validateValidator checks extracted values against the original French pages, not the translation. A separate translation check confirms the English title and description preserve meaning (back-translation or a judge prompt). A failed translation check is a flagged field like any other.
reviewTranslated records carry a "translated" marker. Reviewer sees French and English side by side for title and description.
loadStore source language, the original title and description, and the English versions. Downstream consumers read English; the original stays for audit.
