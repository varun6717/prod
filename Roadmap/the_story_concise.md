## Slide 2: Roadmap

**How to read it**

1. Now = this PI · Next = when Now frees up · Later = blocked or uncommitted.
2. Relative waves, not dates.
3. Boxes are outcomes; backlog items sit behind them.

### Lane 1: Usability and Reliability · *Start with the basics*

1. **Why first:** nothing matters if POs don't trust the tool.
2. **Now, users current:** fixes don't reach everyone → every user gets the latest fixes, sees what changed.
3. **Now, calendar fix:** saved PI calendar runs out Feb 2027 → switch to the live calendar.
4. **Next, less friction:** refine and re-submit an epic in place.
5. **Next, API work:** more usable for API projects; visuals for PMO and Architecture conversations.
6. **Bridge:** short, quick, concrete; buys credibility.

### Lane 2: Product Knowledge Base · *The foundation*

1. **Why it matters:** the strategic bet; initiatives start near zero on product context.
2. **The gap:** Knowledge Hub = summarized code (architecture / engineering view). Custom Product KBs complement it, not replace it.
3. **Now, one model:** one agreed template for describing a product (areas, capabilities, systems, owners). Pilot with Vault.
4. **Now, a KB that learns:** KB should recursively learn and get smarter. Groundwork now: check where each fact came from → see what the KB got right, wrong or missed.
5. **Next, live and governed:** KB live for pilot areas, an owner per area; gaps queued for the owner.
6. **Later, the loop closes:** Jira and ServiceNow history becomes product context; approved fixes update the KB automatically (closes the loop from Now).
7. **Bridge:** almost everything below depends on this row.

### Lane 3: Governance and Standardization · *The guardrails*

1. **Why it matters:** we must be able to stand behind what POP produces.
2. **Now, one Jira policy:** tool, docs and users all agree (today they don't).
3. **Now, sign-off:** every publish records who reviewed it and when.
4. **Next, close the loop:** delivered vs. asked for; requirements traced to code.
5. **Next, auditable artifacts:** version and source stamp on every artifact.
6. **Next, spec-driven development standard:** one standard for spec detail, approval and Dev hand-off.
7. **Bridge:** close-out is the route to the traceability goal and to realized value.

### Lane 4: Cross-Impact Analysis · *The payoff*

1. **Why it matters:** where the first three rows pay off.
2. **Now, shared services early:** POP flags impacted shared services at drafting, well before PBR 3.
3. **Next, engines own their piece:** an epic per impacted engine, handed to that engine's PO.
4. **Later, impact up front:** describe a change, see what it touches (UPG → Boarding).
5. **Later, portfolio check:** new initiative vs. portfolio and strategic roadmap; overlaps found early.
6. **Why the order matters:** needs the Knowledge Base (row 2) and the policy (row 3) first.

### Lane 5: Metrics · *How we will know*

1. **Why it matters:** how we hold ourselves to account; six categories aligned to Neuro OKRs.
2. **Now:** adoption, onboarding, quality, governance.
3. **Next:** speed (needs a "Pod accepted" definition).
4. **Later:** realized value (needs close-out).
5. **Bridge:** walk through them.

## Slide 3: Metrics

**Say once, up front**

1. Only the first headline number is real data.
2. "Illustrative" = preview of the dashboard.
3. Show the shape now, fill in real numbers as they arrive.

### 1. Adoption (actual data)

1. **Question:** how many who could use Neuro are using it?
2. **Number:** 33%, up from 28% (October).
3. **Candid part:** mostly smaller headcount, +10 users; 44% installed, a quarter of those inactive.
4. **Watch instead:** sustained real use, and PO experience.

### 2. Onboarding

1. **Question:** how fast do new POs reach first real output?
2. **Why:** is getting started still a barrier?
3. **Use:** shows who is stuck.

### 3. Quality

1. **Question:** approved at governance first time?
2. **Why:** each rejection is a review cycle and lost time.
3. **Guardrails:** was Pod handoff truly ready; defects flat as speed rises.
4. **Point:** faster only counts if quality holds.

### 4. Governance

1. **Question:** how well-sourced is what POP writes?
2. **Why:** no automated way today to spot unsourced claims → can't fully trust it. Identifying them makes it trustworthy and lets us track improvement.
3. **Measure:** share of claims with no traceable source. Manual sample today; every document once automated.
4. **Tells you:** how much is unsourced; each such claim reviewed by a person before publish, so nothing unsourced reaches governance unchecked.
5. **Alongside:** KB answers usable; requirements traceable to code.
6. **Roadmap link:** traceability goal comes online with close-out.

### 5. Speed

1. **Question:** how long to get work ready for a Pod?
2. **Why this one:** POP's direct share of the Speed OKR.
3. **Behind it:** idea-to-production (whole Neuro programme).

### 6. Realized Value

1. **Question:** did initiatives deliver the outcomes promised? The one that matters most.
2. **Why last:** outcomes show months after go-live; needs close-out.
3. **Reporting:** contribution, not proof of cause.
4. **Point:** moves the conversation from activity to value.
